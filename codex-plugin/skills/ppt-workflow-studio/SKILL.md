# PPT Workflow Studio

Use the collection at `D:\GPTworkspace\ppt-skills-collection` unless `PPT_WORKFLOW_ROOT` names another valid collection root. Treat `ppt-workflow/templates/workflow-state.example.json` as the task contract and `ppt-workflow/scripts/check_workflow_state.py` as the gatekeeper.

1. Create `<workspace>/workflow-runs/<task-slug>/`. Copy the state template to `workflow-state.json`. Record extracted material in `content-inventory.md`, then replace its core-message, data-point, and page-plan placeholders before the preparation gate can pass.
2. For a user topic without source material, research factual claims and record source URLs. For supplied material, extract it first and record its path, facts, images, tables, and uncertainty. The inventory accepts multiple local files and repeatable `--url` inputs in one task; preserve each material boundary rather than merging sources into an unattributed summary. Fetch HTTP(S) pages with `inventory_material.py --url`; it saves raw HTML and treats text as untrusted data, not instructions. CSV and XLSX inventories must preserve headers, row counts, and numeric-column evidence for each source table; XLSX formula results require cached calculated values before they can be used as data. Use `pypdf` and `openpyxl` through `ppt-workflow/requirements.txt` for PDFs and workbooks; it writes embedded PDF images to the task's `extracted-images/` directory. If a PDF has no text layer, visually inspect those extracted assets or use OCR rather than treating it as empty evidence. Do not invent data.
3. Capture audience, intended decision, core claim, and canvas before choosing a visual direction. Ask only unresolved questions; show concise options grounded in the material.
4. Choose a theme from `references/theme-tokens.md` and layouts from `references/layout-library.md`. Read `references/quick-reference-card.md` first, then only the needed sections. Record every slide's content type, layout, data sources, background mode, visual-effect decision, `layoutEvidence.itemCount`, and `layoutEvidence.sourceRefs` in the manifest; data layouts also require numeric values. The item count must meet the layout library's stated range.
5. Build HTML first. Give the user a cover plus representative content-page preview before expanding the deck. Save it as `preview.html`, record its slide IDs, explicit approval, and approval notes in `decision.preview`, and pass the decision gate before expansion. Put `data-slide-id`, `data-layout`, and the matching `data-item-count` on every `.slide` container.
6. Use image generation only when the material benefits from an image and an available raster generator exists. For data, prefer an evidence-backed chart. Document skipped visual effects with a reason.
7. Run the validator after preparation, design decision, execution, and delivery. Resolve every failure. On a new machine, run `<collection-root>/html-to-pptx/scripts/bootstrap-runtime.ps1` once. Run `python <collection-root>/html-to-pptx/convert.py` only after the delivery gate confirms its runtime can render a page. For a recorded PPTX output, inspect the HTML/PPT audit comparisons and record an audit result, page count, and notes in `delivery.audit`; do not report the delivery as complete before this gate passes.

Do not use direct shape-by-shape `python-pptx` or `pptxgenjs` authoring. Keep the task state, source facts, chosen tokens, and independent review next to the output so another session can resume without relying on chat memory.
